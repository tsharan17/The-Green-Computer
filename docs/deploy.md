# Deploying The Green Computer

Two supported shapes:
- self-hosted, on one machine or VM with Docker Compose, or without containers;
- the hosted product on free tiers: Render (web service), Neon (PostgreSQL) and Cloudflare R2
  (files), described below and in `render.yaml`.

Self-hosting needs no external SaaS. Error webhooks and telemetry are optional and off by default.

> Status: the Dockerfile and `docker-compose.yml` are written and checked for syntax, but Docker
> was not available in the development environment, so the images have **not** been built or run
> there. The app, migrations and a multi-user journey **were** run on PostgreSQL 16 (see
> IMPLEMENTATION_STATUS.md). Treat the first container run as a smoke test.

## What every deployment needs

| Need | Why |
|---|---|
| PostgreSQL 14+ (`GC_DB_URL=postgresql+psycopg://…`) | several workers, shared rate limits, backups |
| A persistent data directory (`GC_DATA_DIR`) | uploaded files, exports, `server.key`, `agent_signing.key`, `installation_id` |
| HTTPS in front (reverse proxy or the platform) | Secure cookies; device agents refuse plain http except to localhost |
| `GC_ENV=production`, `GC_PUBLIC_URL=https://your-host` | Secure cookies, no development links in responses, correct links in emails |
| SMTP (`GC_SMTP_*`) | password reset and email confirmation (`GC_REQUIRE_EMAIL_VERIFICATION=1` needs it) |

Health checks:
- `GET /api/v1/health` is liveness.
- `GET /api/v1/ready` is readiness: database reachable, schema at the latest migration, file
  storage writable. It answers 503 otherwise.

Migrations run at start-up (`GC_AUTO_MIGRATE=1`). With several instances, set
`GC_AUTO_MIGRATE=0` and run `python -m alembic upgrade head` once per release before starting them.

## Self-hosted with Docker Compose

```
cp .env.example .env            # set GC_PUBLIC_URL, GC_POSTGRES_PASSWORD, SMTP
docker compose up --build -d
docker compose ps               # app becomes "healthy" when /api/v1/ready answers 200
```

The compose file runs PostgreSQL 16 and the app (one uvicorn worker) with named volumes for the
database and files. Put a TLS-terminating proxy in front, for example Caddy:

```
gc.example.com {
    reverse_proxy 127.0.0.1:8000
}
```

and set `GC_TRUST_PROXY=1` so client addresses (for rate limits and the audit log) come from
`X-Forwarded-For`.

### More workers

The rate limiter is shared through PostgreSQL, so you can raise uvicorn `--workers`. Two rules:
- run migrations once, separately (`GC_AUTO_MIGRATE=0` on the workers);
- keep `GC_DATA_DIR` on storage every worker sees.

Local execution runs one model at a time per workspace; it is enforced in the database.

## Self-hosted without containers (systemd)

```
python3.12 -m venv /opt/gc/venv
/opt/gc/venv/bin/pip install "/opt/gc/src/backend[postgres]"
cd /opt/gc/src/frontend && npm ci && npm run build      # writes backend/app/static
```

`/etc/systemd/system/green-computer.service`:

```
[Service]
User=gc
EnvironmentFile=/etc/green-computer.env
WorkingDirectory=/opt/gc/src/backend
ExecStart=/opt/gc/venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8000 --workers 2 --proxy-headers
Restart=on-failure
```

Retention on a timer (daily):

```
ExecStart=/opt/gc/venv/bin/python /opt/gc/src/scripts/retention.py --apply
```

## Hosted on free tiers: Render + Neon (+ Brevo for email)

`render.yaml` at the repository root describes the service. **Status: written and tested piece by
piece (database and S3 blob stores, hosted mode, URL handling); live since 2026-11-03.**

| Piece | Service | Free-tier limits that shape the setup |
|---|---|---|
| App (API + web UI, one container) | Render, free web service, Docker | About 512 MB RAM and a fraction of a CPU; sleeps after 15 idle minutes; no persistent disk |
| Database, uploaded files and exports | Neon, free project | 0.5 GB storage; suspends when idle (the app tests each pooled connection before use) |
| Email | Brevo, free plan, over HTTPS | 300 messages a day; the sender address is verified in Brevo, no domain needed. Render's free plan blocks outgoing SMTP, so Gmail or any SMTP relay cannot be used there |

Files are kept in the database (`GC_BLOB_BACKEND=database`) so no object store is needed. With
more users, or a domain of your own, switch to Cloudflare R2 (`GC_BLOB_BACKEND=s3`, below) and a
sending service such as Resend. Free-tier terms change; check each provider's current limits.

What the configuration does, and why:
- `GC_HOSTED=1`: rate limits and caps on, uploads capped (`GC_MAX_UPLOAD_MB`, default 50), and
  **nothing is executed on the server**: timed runs and INT8 conversion are refused with a message
  pointing to a paired device. Predictions, the digital twin, plans and exports all work.
- `GC_SECRET_KEY` and `GC_AGENT_SIGNING_SECRET` are generated by Render. With `GC_HOSTED=1` the
  server refuses to start without them, because keys created on a disk that is wiped on restart
  would break two-step sign-in and paired devices.
- `GC_BLOB_BACKEND=database` keeps files in the `blobs` table of the app's database (read copies
  are cached on the container's disk). Simplest on a free plan; watch the database size.
- `GC_BLOB_BACKEND=s3` with `GC_S3_ENDPOINT`, `GC_S3_BUCKET`, `GC_S3_ACCESS_KEY_ID`,
  `GC_S3_SECRET_ACCESS_KEY` (and optionally `GC_S3_REGION`, default `auto`, and `GC_S3_PREFIX`).
  Files keep their per-workspace keys; deleting a workspace deletes its objects.
- `GC_DB_URL` can be pasted from Neon as it is (`postgresql://…?sslmode=require`); the app switches
  the scheme to its psycopg driver.
- The container listens on `$PORT` when the host sets it (Render does), else 8000.

Steps:
1. Neon (sign in with GitHub): create a project on an account separate from any other deployment
   (Postgres 16 or later, a region near your users); copy its connection string.
2. Brevo: create a free account, add and verify the sender address (Senders, Domains & Dedicated
   IPs, Senders), then create an API key (SMTP & API, API keys).
3. Render (sign in with GitHub): New, Blueprint, pick this repository. Paste the two secrets,
   `GC_DB_URL` and `GC_BREVO_API_KEY`. If Render's address differs from `GC_PUBLIC_URL` in
   `render.yaml`, set the real one in the dashboard.
4. With R2 instead of the database for files: create a bucket and an API token with object read and
   write on that bucket, and set `GC_BLOB_BACKEND=s3` and the four `GC_S3_*` values.
   Render's free plan blocks outgoing SMTP: email must go through an HTTPS API (Brevo here).
   Linked by the repository's public address, Render does not deploy on push: use Manual Deploy,
   Deploy latest commit, or connect Render's GitHub app.
5. Check `https://<host>/api/v1/ready`, then run `python scripts/acceptance.py https://<host>`.
6. UptimeRobot (or similar): poll `/api/v1/ready` every 5 minutes to avoid cold starts and get
   alerts. This uses most of Render's free monthly hours for one always-on service.
7. Security checks on the live URL, before announcing it:
   - sign up two accounts in two browsers; with the second, open the first one's project, export
     and artifact links (copy them from the first browser): each must say "not found";
   - with a domain on Cloudflare: proxy the host (orange cloud), turn on Bot Fight Mode, and add a
     rate-limiting rule on `/api/v1/auth/*` (for example 20 requests a minute per IP, then block
     for 10 minutes). The app's own limits stay on behind it;
   - confirm `GC_TRUST_PROXY=1` is set, so the app limits by the visitor's address and not the
     proxy's;
   - leave `GC_METRICS_TOKEN` unset unless something scrapes `/metrics`.

Memory, measured on the development machine (Windows working set, one user): about 125 MB after
start-up, about 145 MB after analyses, about 225 MB after drawing figures and exporting a PDF
(matplotlib loads on first use). Treat these as rough; measure on the host.

## Configuration reference

Every setting is an environment variable listed with comments in `.env.example`. Hosting adds
`GC_HOSTED`, `GC_MAX_UPLOAD_MB`, `GC_BLOB_BACKEND` and `GC_S3_*`. Release 2 adds:
- `GC_SECRET_KEY` and `GC_AGENT_SIGNING_SECRET`;
- `GC_REQUIRE_EMAIL_VERIFICATION` and `GC_RATE_LIMIT_BACKEND`;
- `GC_LOG_FORMAT`, `GC_LOG_LEVEL`, `GC_LOG_IPS`;
- `GC_METRICS_TOKEN`;
- `GC_ERROR_REPORTER`, `GC_ERROR_WEBHOOK_URL`, `GC_SENTRY_DSN`;
- `GC_GIT_SHA`;
- `GC_TELEMETRY`, `GC_TELEMETRY_URL`.

## Monitoring

- Scrape `GET /metrics` with `Authorization: Bearer $GC_METRICS_TOKEN`. It provides:
  - request counts and duration histograms by route template;
  - unhandled errors and uptime;
  - whether rate limiting is shared.
- Alert on `/api/v1/ready` failing, on `gc_unhandled_errors_total` increasing, and on the p95 of
  `gc_http_request_duration_seconds` for `/api/v1/projects/{project_id}/optimise`.
- With `GC_LOG_FORMAT=json` each request is one JSON line with `request_id`, which users can quote
  from error messages.
